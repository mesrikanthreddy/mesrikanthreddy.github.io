slower** with AI tools, yet believed they were **20% faster**<sup>[1](#ref-1)</sup>. A year
later, the same lab said its follow-up data had become "an unreliable
signal", because 30–50% of developers were withholding tasks they didn't
want to do without AI<sup>[2](#ref-2)</sup>. Both results point at the same problem: we
are producing code faster than we can tell whether it is right.

## Abstract

For most of software's history, the expensive part of building a system was
turning an idea into working syntax. That cost has collapsed: modern AI
coding agents produce idiomatic, working code in almost any language or
framework, faster than a person can describe it.

This paper argues that syntax was never the real constraint. It was the most
*visible* one. In Fred Brooks's terms, it was accidental complexity, not
essential complexity<sup>[3](#ref-3)</sup>. With it removed, three harder problems are now exposed:
**specifying intent**, **verifying correctness**, and **owning systems over
time**. Teams that only optimize for code output risk shipping more code
without shipping more working products. Teams that reorganize around these
three problems are better placed to benefit.

The second half of the paper is practical. It proposes a working loop,
**Intent → Verify → Own**, and turns each step into concrete artifacts: a
one-page intent spec, a layered verification ladder, and ownership practices
that keep a system understandable after the conversation that generated it
is gone. Along the way it reports a reading of 2,731 developer comments from six Hacker News threads (§5) and an audit of a real public repository (§7). It is explicit about its limits: the method is a proposal, not a validated result, and §9 says how to test it.

## 1. What "solved" actually means

"Syntax is solved" does not mean AI writes perfect software. It means:

- Translating a clearly stated behavior into code in a given language is no
  longer a scarce skill.
- Learning a new framework, SDK, or language is no longer a multi-week cost
  before you can be productive.
- Boilerplate, glue code, migrations, test scaffolding, and refactors that
  used to eat days now take minutes.

The speed is measurable. In a controlled experiment, developers with GitHub
Copilot finished a programming task 55.8% faster than those without it<sup>[4](#ref-4)</sup>,
and AI agents are now routinely evaluated on resolving real GitHub issues in
real repositories, not toy problems<sup>[5](#ref-5)</sup>.

The phrase that matters is *clearly stated behavior*. When the input is precise, the output tends to be right. When it is wrong, the cause is often upstream: the request was ambiguous, incomplete, or quietly contradicted something else in the system.

In other words, the error has moved. It used to live in the code. Now it
lives in the gap between what someone meant and what they said.

That's why faster typing hasn't straightforwardly meant faster delivery. In
the 2025 trial, 16 experienced open-source developers working on their own
mature repositories took 19% *longer* when allowed to use AI, while believing
afterwards that it had made them 20% faster<sup>[1](#ref-1)</sup>. Read that as a result
about *perception versus measurement*, not a verdict on AI. The sample was
small and the tools were early-2025 models. METR's February 2026 follow-up,
using late-2025 tools, found −18% for returning developers and −4% for new
ones, both with intervals wide enough to include a speedup. METR itself calls
that data an unreliable signal and a likely *lower bound* on the true
effect<sup>[2](#ref-2)</sup>. What survives both studies is a narrower, sturdier finding:
a developer's own sense of speed is a poor instrument, and measuring this
properly is hard.

The organizational data points the same way. Google's 2024 DORA report
associated a 25% increase in AI adoption with a 7.2% drop in delivery
stability and a 1.5% drop in throughput<sup>[6](#ref-6)</sup>. In the 2025 report, with
90% of respondents now using AI at work, the throughput relationship turned
positive, but the stability relationship stayed negative, because
"acceleration can expose weaknesses downstream"<sup>[7](#ref-7)</sup>. Developers feel it:
in Stack Overflow's 2025 survey of over 49,000 developers, 84% use or plan to
use AI tools, yet 46% don't trust their accuracy, up from 31% a year
earlier<sup>[8](#ref-8)</sup>. Code got cheaper. Software didn't get automatically better.

## 2. The next problem: intent

### 2.1 Specification is the new source code

When a model can write any code you describe, the description *becomes* the
program. A vague prompt is the new buggy function. The work that matters is
now:

- Defining the problem in terms of observable behavior, not implementation.
- Stating constraints that were always implicit: performance budgets, data
  residency, failure modes, who is allowed to see what.
- Naming the edge cases before the code exists, not after the incident.

Engineers who are good at this were always valuable. The gap between them and everyone else is likely to widen, because the people who can't do it are amplified in the wrong direction: AI will produce confident, plausible code that solves the wrong problem.

The research bears this out. In a study of 517 Stack Overflow questions, 52%
of ChatGPT's answers contained incorrect information, and the most common
category was *conceptual* error (misunderstanding the question), not broken
code. Users still preferred those answers 35% of the time and missed the
errors 39% of the time<sup>[9](#ref-9)</sup>.

### 2.2 Context is the scarce input

A model writing a function sees the function. It doesn't see the decision
made eighteen months ago about why that service retries only twice, the
regulatory reason a field is never logged, or the client who will churn if
an export format changes. That knowledge lives in people, tickets, and
tribal memory.

DORA's 2025 report lists connecting AI to internal context among the capabilities that make its benefits larger<sup>[7](#ref-7)</sup>. In practice that means turning context into something an agent can read: architecture decision records, project-level instruction files, documented conventions, and schemas that encode business rules instead of hiding them. Context engineering is becoming a core engineering discipline.

More context isn't automatically better context. Language models make
noticeably worse use of information placed in the middle of a long input than
at its beginning or end<sup>[10](#ref-10)</sup>. Pasting the whole wiki into the prompt isn't a
strategy. Deciding what the model needs to see, and putting it where the
model will use it, is.

## 3. The problem after that: verification

If code is cheap to produce, the cost of software shifts to the question
*"is this right?"* That question is harder than it sounds.

- **Volume outpaces review.** An engineer with an agent can generate far more diff than anyone can review carefully, line by line, and developers say so themselves (§5.2).
- **Plausible is not correct.** AI-written code tends to look clean and
  idiomatic, which removes the visual cues reviewers have always relied on
  to spot sloppy work. When researchers had GitHub Copilot complete 89
  security-relevant scenarios, about 40% of the 1,689 generated programs
  were vulnerable<sup>[11](#ref-11)</sup>. In a separate user study, participants with an AI
  assistant wrote significantly less secure code *and* were more likely to
  believe their code was secure<sup>[12](#ref-12)</sup>.

- **Tests can be wrong in the same way.** When the same system writes the
  code and the tests from the same misunderstanding, the suite passes and
  the bug ships. Weak tests hide wrong code at scale: when researchers
  expanded a widely used code-generation benchmark with 80x more test
  cases, measured pass rates dropped by up to 28.9%<sup>[13](#ref-13)</sup>.

The answer isn't more manual review. It's moving verification to places
where it scales:

1. **Executable specifications.** Acceptance criteria written as tests
   *before* generation, by someone who understands the intent.
2. **Boundaries enforced by the system, not the reviewer.** Type systems,
   database-level security policies, contract tests between services, and
   CI gates that block merges outright.
3. **Observability as verification.** In production, the real test is
   whether the system behaves as intended under real load and real data.
   Monitoring, tracing, and alerting become part of the definition of
   "done."
4. **Human review aimed at risk.** People spend their attention on
   security boundaries, data handling, money movement, and irreversible
   operations, not on formatting and naming.

## 4. The hardest problem: ownership

Writing code is usually a small part of what a system costs over its life. Running it for years is the expensive part: upgrades, incidents, schema
migrations, cost control, compliance audits, and the slow drift between what
the system does and what the business now needs. Lehman observed this in
1980: software in real use must keep changing, and its complexity grows
unless work is done to reduce it<sup>[14](#ref-14)</sup>.

AI lowers the cost of creating software, which means organizations are likely to create *more* of it. Every new service, integration, and internal tool is a
long-term liability as well as an asset. The new failure mode isn't "we
couldn't build it." It's "we built forty things and nobody understands
thirty of them."

Early data points the same way. One industry analysis (not peer-reviewed) of 153 million changed lines of code found code churn (lines reverted or rewritten within two weeks)
rising sharply alongside AI adoption, with copy-pasted code growing faster
than refactored or moved code<sup>[15](#ref-15)</sup>. This isn't new for AI-heavy systems:
Google engineers warned in 2015 that in production ML systems, the code is a
small fraction of the system and the surrounding infrastructure is where the
long-term debt accumulates<sup>[16](#ref-16)</sup>.

Ownership in this world means:

- **Fewer, better-understood systems** over many disposable ones.
- **Architecture that an agent and a new hire can both read**: clear module
  boundaries, documented decisions, consistent conventions.
- **Operational maturity as a first-class skill**: infrastructure as code,
  reproducible environments, cost visibility, and incident response that
  doesn't depend on whoever wrote the original code.

Peter Naur argued in 1985 that a program's real value is the *theory* of it
held in the heads of the people who built it, and that a program whose theory
has been lost is effectively dead even if it still runs<sup>[17](#ref-17)</sup>. AI-generated
systems are at risk of being born without that theory. The prompt
conversation that produced them is gone, and nobody ever held the full model
of the system in their head.

This is where deep infrastructure and production experience arguably becomes *more* valuable, not less. Generating a service is easy. Knowing what happens when
it meets a real network, a real compliance auditor, and a real 2 a.m. outage
is not.

## 5. What developers are saying

Studies measure outcomes. They don't show how practitioners reason about the
problem while living with it. So I read what developers wrote in six
high-engagement Hacker News threads about AI-assisted coding: 3,049 comments,
2,731 of them long enough to analyse (15 words or more), from 1,428 different
people. I coded them for the themes in this paper and for some I hadn't
planned on.

This is a **qualitative reading with keyword assistance, by one coder**, of one
website that skews toward working software engineers. It shows what
developers argue about, not how common any view is in the industry, and it
measures nothing about code quality or speed. The method, the keyword lists,
and a hand-check of their accuracy are below, and the scripts are published
in the [study folder](/research/forum-study/README.md).

## 6. The solution: the Intent → Verify → Own loop

Each of the three problems has the same root cause: something that used to
happen *implicitly*, as a side effect of a human typing the code, now happens far less. When you wrote every line yourself, you were forced to
resolve ambiguity, you noticed when something looked wrong, and you
understood the result because you built it. AI removed the typing, and with
it the accidental quality control.

The fix is to make each of those steps *explicit*: give each one an
artifact, put it in the repository, and enforce it with tooling instead of
good intentions.

### 6.1 Solving intent: write the spec before the prompt

Code is now cheap to regenerate, so iterate on the *specification* and let
the code follow. Before any non-trivial change, write a one-page intent spec.
It doesn't need a tool or a process. A Markdown file in the repository is
enough:

```markdown
# Intent: <feature name>

Goal        What outcome, for whom, and why now.
Must        Observable behaviors, stated so a test could check them.
Must never  The things that would make this a failure: data leaks,
            double charges, silent errors.
Edge cases  Empty, huge, duplicate, concurrent, offline, unauthorized.
Constraints Performance budget, data residency, cost, compliance.
Done when   The acceptance tests that must pass, written in plain language.
```

**Take it with you:**
<a href="/templates/intent-spec.md" download>intent-spec.md</a> (the template,
with a short worked example) and
<a href="/templates/agent-context-example.md" download>agent-context-example.md</a>
(a starter project instruction file for your coding agent).

Three practices make this work:

1. **Make the agent interrogate the spec first.** Before generating code,
   ask the model to list every ambiguity, assumption, and missing edge case
   it sees, and to propose a plan. Answering those questions takes minutes
   and resolves the conceptual errors that were the most common kind of mistake in one study of ChatGPT answers<sup>[9](#ref-9)</sup>.
2. **Treat "must never" as the most important section.** Models are good at making things work. They tend to be worse at knowing what must not happen, because that knowledge is usually unwritten. Writing it down is arguably the highest-leverage part of the spec.
3. **Turn context into code.** Keep project instruction files (conventions,
   architecture, forbidden patterns, the "why" behind odd decisions) in the
   repository, versioned and reviewed like code. Keep them short and put the
   rules that matter most first, since models tend to use the beginning and end of their context best<sup>[10](#ref-10)</sup>. Layer them: organization-wide rules, then
   per-project rules, then per-directory rules, so each task loads only the
   context it needs.

### 6.2 Solving verification: build a verification ladder

The goal isn't to review more. It's to make sure that by the time a human
looks at a change, everything a machine *can* check has already been
checked. Each rung of the ladder catches a different class of failure:

| Rung | What it catches | Examples |
| --- | --- | --- |
| 1. Types and schemas | Shape errors, missing fields, wrong contracts | Strict TypeScript, typed API schemas, database constraints |
| 2. Tests from the spec | Wrong behavior | Acceptance tests written from "Must" and "Done when", before the code |
| 3. Policy in the system | Authorization and data-access mistakes | Row-level security, one central authz layer, contract tests |
| 4. Security scanning | Known vulnerability patterns, leaked secrets | Static analysis and secret scanning on every diff |
| 5. CI gate | Anything above being skipped under pressure | Nothing merges unless rungs 1–4 pass |
| 6. Production signals | What only real traffic reveals | SLOs, tracing, alerts, feature flags, fast rollback |
| 7. Human review by risk | Judgment calls machines can't make | Required review only for auth, money, PII, migrations, irreversible ops |

Two rules hold the ladder together:

- **Separate the author from the judge.** The tests that define "correct"
  should not come from the same misunderstanding as the code. Write
  acceptance tests from the spec first, by a human or in a separate agent
  session that has never seen the implementation. Then generate the code to
  pass them. Weak, self-written tests are exactly how wrong code survives
  evaluation<sup>[13](#ref-13)</sup>.
- **Never let confidence stand in for evidence.** In the studies above, developers using AI overestimated their speed<sup>[1](#ref-1)</sup> and the security of their code<sup>[12](#ref-12)</sup>. The
  ladder exists so that "it looks right" is never the reason something ships.
  Security-relevant code in particular gets scanned automatically every time,
  because roughly 40% of generated code in security-sensitive scenarios has
  been shown to be vulnerable<sup>[11](#ref-11)</sup>.

### 6.3 Solving ownership: keep the theory alive

If a program's value is the theory of it held by its builders<sup>[17](#ref-17)</sup>, the
job is to make sure that theory is written down and owned by someone, rather
than lost when the chat window closes.

- **Commit the intent with the code.** The spec from §6.1 lives in the
  repository next to the feature it describes. The conversation that
  produced the code is temporary. The spec is the durable record of what was
  meant.
- **Write a decision record for anything surprising.** One short paragraph:
  what was decided, what was rejected, and why. Future engineers and future
  agents both read it, and it stops the next change from undoing a
  deliberate choice.
- **Pass the explain-back test before merge.** The person merging a change
  must be able to explain what it does and why, without the AI open. If they
  can't, it isn't ready, however green the tests are.
- **Give every system a named owner and a runbook.** "The team" is not an
  owner. Someone is accountable for each service's health, costs, and
  upgrades, and the runbook means an incident doesn't depend on whoever
  happened to prompt it into existence.
- **Budget for deletion.** Cheap creation needs a counterweight. On a fixed
  cadence, retire, merge, or simplify systems, because complexity grows
  unless someone deliberately works against it<sup>[14](#ref-14)</sup>.
- **Measure stability, not output.** Track change failure rate, time to
  restore, and code churn alongside delivery speed<sup>[6](#ref-6)</sup><sup>,</sup><sup>[15](#ref-15)</sup>. If AI is helping, these should hold steady or improve. If only speed improves, debt may be accumulating somewhere you aren't looking.

### 6.4 The loop in practice

Here's the loop applied to a small, realistic change. This is a hypothetical walkthrough, not a case study (§7 has the real audit): *add partial refunds to an existing payments service.*

1. **Intent.** A one-page spec. *Must:* refund any amount up to the
   remaining captured balance. *Must never:* refund more than was captured,
   refund twice on a retried request, or let a non-admin trigger a refund.
   *Edge cases:* concurrent refunds, currency rounding, provider timeouts.
2. **Interrogate.** The agent reads the spec and the project context files,
   then asks: is the idempotency key client-supplied or server-generated?
   What happens if the provider succeeds but our database write fails? Both
   questions get answered in the spec, not discovered in production.
3. **Verify first.** Acceptance tests are written from the "Must" and "Must
   never" lines, including a concurrent double-refund test, before any
   implementation exists.
4. **Generate.** The agent writes the implementation to pass those tests,
   inside the existing types, authorization layer, and database constraints.
5. **Climb the ladder.** Type check, tests, security scan, and CI gate run
   automatically. Because this touches money, a human review is required,
   and it focuses on the idempotency and failure-handling paths.
6. **Ship behind a flag.** Refund volume, failure rate, and provider errors
   get alerts. Rollback is a flag flip.
7. **Own.** The spec is committed with the code, the "server-generated
   idempotency key" choice gets a decision record, and the payments
   service's owner updates its runbook.

None of these steps needs to be slow, and most should take minutes. Together they give a fast change a much better chance of also being a correct one.

### 6.5 Adopting it in 30 days

You don't need a reorganization to start. Pick one active repository and
add one layer a week:

- **Week 1: context.** Add a project instruction file and the intent-spec
  template. Require a spec for any change bigger than a bug fix.
- **Week 2: the gate.** Turn on strict types, a security scanner, and a CI
  gate that blocks merges on failure.
- **Week 3: tests first.** For one feature, write acceptance tests from the
  spec before generating any code, and compare the outcome with how you
  worked before.
- **Week 4: measure.** Record a baseline for change failure rate, time to
  restore, and churn. From then on, judge AI tooling by whether these move
  in the right direction, not by how much code it produces.

After a month you should have a repository that an agent and a new hire can both start from with far less guesswork. That is a better measure of success than lines of code.

### 6.6 Starting thresholds

"Write a good spec" and "verify automatically" are only useful if you can
tell when you've done them. These are the checks I'd start with. They are
defaults chosen because each one is a yes/no question or something a machine
can enforce. They are **not derived from data**, so tune them to your context
and your risk tier (§9.1).

| Area | Check | Pass when |
| --- | --- | --- |
| Intent | Every "Must" is observable | A test could be written from the line alone, without asking the author |
| Intent | Trust boundaries are covered | Each boundary the change touches (auth, money, personal data, external calls) has at least one "Must never". If it touches none, the spec says so |
| Intent | Edge cases are resolved | Each listed edge case maps to a test or to an explicit "out of scope" note |
| Intent | The spec stays small | It fits on one page. If it doesn't, split the work |
| Verify | The gate is the policy | Rungs 1 to 5 are required checks on the default branch, and none can pass by being skipped or swallowed (no `\|\| true`, no `\|\| echo`) |
| Verify | Traceability | Every "Must" and "Must never" has at least one automated test |
| Verify | Scanner findings | No new high or critical finding stays open. A waiver needs a written reason and an expiry date |
| Verify | Human review | Required for the high-stakes tier, enforced by code ownership on auth, payments, migrations, and personal-data paths |
| Own | A named owner | Every deployed system has one person accountable, recorded in the repository |
| Own | Explain-back | The person merging can say what changed, why, and how it fails, without the AI open |
| Own | A written *why* | Anything surprising has a decision record, a changelog entry that gives the reason, or a code comment that does |
| Own | A retirement review | Each system is reviewed for simplification or retirement at least every six months |

Treat a failed check as a prompt to look, not as proof of a bad change.
Section 7 shows what scoring a real repository against these rungs looks
like.

| --- | --- | --- |
| 1. Types and schemas | Partial | Rust is compiled in CI, the dashboard runs `tsc --noEmit`, and the VS Code extension is compiled. The Python backend has no type checker or linter configured, and the Rust code has no `clippy` or `fmt` check |
| 2. Tests from the spec | Partial | 186 backend test functions across 9 files, which matches the changelog's count, plus `cargo test` in CI. But `backend/tests/` is gitignored: none of those tests are tracked, so a fresh clone has none |
| 3. Policy in the system | Absent, disclosed | `SECURITY.md` states that the backend API has no authentication on any endpoint. That is acceptable for the default `127.0.0.1`-only install and risky behind `docker-compose.yml` or a shared host |
| 4. Security scanning | Present | CodeQL for Python and JS/TS on pushes to `dev` and `master`, on every PR, and weekly. Dependabot weekly across Rust, Python, and npm. kshield also scans the changed files of every PR |
| 5. CI gate | Absent | Checks run on pull requests, but GitHub reports `master` as not protected and there are no rulesets, so nothing requires checks to pass, or a review, before a merge. The backend test step is `pytest tests/ -v \|\| echo "No tests yet"`, which succeeds whether the tests pass, fail, or don't exist |
| 6. Production signals | Not applicable | A local-first tool with no hosted service. I found no telemetry or error reporting in the backend, CLI, or dashboard code |
| 7. Human review by risk | Partial | A PR template and written review criteria exist, and `CONTRIBUTING.md` says every PR needs a review. Nothing enforces it, and 50 of the repository's 51 commits (across all branches) are by one author |

Ownership practice is stronger than the ladder score. `SECURITY.md` names a contact and a
response time and lists known gaps up front. The changelog records not only
what changed but why, for example the npm package name that turned out to be
squatted and the reasons for rewriting the remediation module. Architecture
notes live in `docs/`. What's missing is per-feature intent specs, a
decision-record directory, and a code-ownership file.

### What the audit found

- **The strongest rung is scanning and the weakest is the gate.** Every
  check exists and none is required to merge. That is the failure rung 5 is there to
  prevent: anything above it being skipped under pressure. A solo maintainer
  in a hurry can merge a red build.
- **The most valuable artifact isn't in the repository.** The 186 tests
  exist and, per the changelog, pass, but they are local only. For a tool
  whose pitch is catching problems before they reach the main branch, its
  own backend tests never get there, and the CI step reports "No tests yet"
  on every run. The changelog already says so, which is a good ownership
  habit. It also means the gap is known and not yet closed.
- **A red CI run that isn't about quality.** The most recent pull request
  run (5 August 2026) is red, although every build, test, and type-check job
  passed. Only the step that posts kshield's review comments failed. I
  haven't diagnosed why. A gate that goes red for reasons unrelated to
  quality teaches people to ignore red.

### What would change

Three small changes would close most of this: track the backend tests (or a
sanitized subset, since the fixtures contain fake secrets) and delete the
`|| echo`; protect `master` with required checks and a review; and add a
Python linter and type checker to CI. Making them would turn this audit into
the first before-and-after measurement for §9.3, and the baseline is
recorded here so the comparison can be honest.

## 8. What changes

### 8.1 For engineers

The role shifts from *author* to *architect, editor, and operator*:

<div className="then-now">

| Then | Now |
| --- | --- |
| Knowing the syntax | Knowing the system |
| Writing the code | Specifying the behavior |
| Reviewing every line | Designing what gets verified, and how |
| Shipping features | Owning outcomes in production |
| Learning a framework | Learning a domain |

</div>

Domain expertise becomes the multiplier. An engineer who understands
energy-grid operations, patent workflows, school administration, or payment
compliance can now build in that domain far faster than before. An engineer who only understood the framework has lost much of their advantage.

### 8.2 For organizations

- **Measure outcomes, not output.** Lines of code, PR counts, and velocity
  points were weak proxies before. Now they're actively misleading, because
  perceived productivity and measured delivery can move in opposite
  directions<sup>[1](#ref-1)</sup><sup>,</sup><sup>[7](#ref-7)</sup>.
- **Make the gate the policy.** If a rule matters, enforce it in CI, the
  type system, or the database, where it can't be skipped under deadline
  pressure (§6.2, and the gap §7 found). Documentation, decision records,
  and agent-readable project files pay back directly in AI output quality
  (§6.1).
- **Hire and promote for judgment.** Problem framing, system design, risk
  assessment, and communication with the business are now the core of the
  job.

## 9. Limits, counterarguments, and how to test this

This paper proposes a method. It does not prove one. The honest status of
each claim is below.

### 9.1 When not to use the full loop

Ceremony should scale with the cost of being wrong. A weekend prototype
doesn't need a verification ladder, and a payments service shouldn't run on a
chat transcript.

| Tier | Example | What to apply |
| --- | --- | --- |
| Throwaway | A one-off script, a spike, a demo | Skim the output. Nothing more. |
| Internal | A tool your team depends on | A short spec, types, a CI gate, a named owner |
| High stakes | Money, personal data, safety, anything irreversible | The full loop: spec, the whole ladder, risk-based human review, decision records |

### 9.2 Likely objections

- **"Models will get better at asking what you meant."** Partly true, and
  §6.1 already asks the agent to interrogate the spec. But a better model
  still can't know the business priority nobody wrote down, or why a field is
  never logged. Better models probably move the bottleneck. They are unlikely to remove it.
- **"This is just waterfall with extra steps."** Waterfall's central problem was slow feedback. Here the spec is one page, the loop is meant to run in minutes, and the durable artifact is a set of tests, not a document nobody reads.
  If your spec grows past a page, that's a signal to split the work.
- **"The evidence is thin."** Fairly. The forum reading in §5 is one
  coder's keyword-assisted reading of one website, so it shows what
  developers argue about, not how common any view is. Several sources here are surveys that
  show correlation, one is an industry report rather than peer-reviewed
  research, most studies predate today's models, and the METR numbers carry
  the caveats described in §1. This paper's claim is structural, namely
  *where* errors moved, not a forecast of how large the effect is in any
  team.

### 9.3 How to test this on your own work

Treat the loop as a hypothesis and measure it:

1. **Baseline first.** For one repository, record change failure rate, time to
   restore service, and code churn for the last quarter<sup>[6](#ref-6)</sup><sup>,</sup><sup>[15](#ref-15)</sup>.
2. **Adopt the loop for 30 days** using the plan in §6.5, on real work.
3. **Compare.** If failure rate and time to restore improve and churn falls,
   the method is earning its overhead for you. If they don't move, the
   method is the wrong fit for your context, and that is a useful result too.

I'd like to see this tested properly: ideally across several teams, with a
control group, using measured outcomes instead of self-reports. That's the
gap between this proposal and a validated result.

## Conclusion

**What changed.** Turning a clear request into working code is now cheap.
That did not make software easier to get right. It exposed where the
difficulty always was. Brooks called the typing *accidental* complexity<sup>[3](#ref-3)</sup>.
What remains is the *essential* part: deciding what to build, proving that it
does that, and being able to run and change it years later.

**What the evidence says.** A developer's sense of their own speed is a poor
guide. In one controlled study, developers felt faster while the measurements
said otherwise, and the follow-up was too distorted to settle it. Delivery
data shows speed rising while stability suffers. And when more than a
thousand developers argue about this in public, the theme that comes up most
is not how to generate code but how to check it, with specifying and owning
it close behind.

**What this paper proposes.** One loop and three questions. **Intent:** can I
state, in testable terms, what this must do and must never do? **Verify:**
what will prove it, and is that check automatic? **Own:** who runs this in
six months, and can they understand it without the conversation that produced
it? In practice: a one-page spec, a ladder of checks that can block a merge,
and a written reason for anything surprising.

**What it has not shown.** This is a proposal. The audit of kshield found the
gap the paper predicts, checks that exist but can't stop a merge, but one
repository is an illustration, not proof. Nobody has yet measured whether
the loop improves outcomes. §9.3 says how to find out.

**What to do this week.** Three small steps. Score one repository with the
[scorecard](/templates/ladder-scorecard.md). Write one intent spec before your
next AI-assisted change and commit it. Make one check blocking, and delete any
`|| true` that lets it pass. Then measure for 30 days, and if the numbers
don't move, say so.

The coding syntax problem is solved. The next problem is intent, and it
has always been ours.
