One of my project instruction files contains this sentence:

> There is no test runner configured anywhere in this repo (no `test` script,
> no Jest/Vitest) — don't assume one exists.

Further down, the same file has a section called "Tests and CI". It describes
the Vitest suite, the database tests and the GitHub Actions workflow that runs
them. Git shows that both passages arrived in the same commit.

The project is Vidya, our multi-tenant school platform. The tests are real:
they cover the one route that can create logins, and the database rules that
decide who can see a student's record. An agent that believes the first passage
has a written instruction not to look for them.

Nothing caught this. The file compiled, because prose always compiles. No
linter complained and no test failed. If two functions in that codebase had
disagreed this plainly, we would have called it a bug. This is also a bug. It
just lives in a file we hadn't been treating as code.

## The starting point

"Context is the new code" is not my line. Patrick Debois, who founded
DevOpsDays, gave talks under that title at AI Engineer Europe 2026<sup>[1](#ref-1)</sup> and
QCon London<sup>[2](#ref-2)</sup>, arguing that context needs a development lifecycle of its
own. A year earlier, Sean Grove made a related case for specifications<sup>[3](#ref-3)</sup>.

"Context is the new code" names the destination. This essay is about the return
trip: we moved away from writing code, and the discipline of code came back.

By context I mean something specific. **Context is everything a model is given besides
its training**: the prompt, instruction files, specs, tool definitions,
retrieved documents and conversation history. It deserves to be called code
because it has the property that matters: change it, and the system behaves
differently.

In [Syntax Is Solved. Intent Isn't.](/writing/syntax-is-solved) I called
context the scarce input to AI-assisted development, and recommended keeping it
in version-controlled files. That was the start of the answer. Version control
tells you what changed. It doesn't tell you whether the file is true, or
whether it helps.

## The uncomfortable evidence

If context is so powerful, adding more of it should make agents better. The
best evidence I found says that it usually doesn't.

Researchers at ETH Zurich and LogicStar.ai tested repository instruction files
(`AGENTS.md`, `CLAUDE.md`) across four agent and model pairings. Their new
benchmark has 138 tasks from 12 Python repositories. The current version of the
paper reports<sup>[4](#ref-4)</sup>:

| File type | Change in task success | Change in cost |
| --- | --- | --- |
| Generated by an LLM | −2% on average, not significant | +20% |
| Written by developers | +2.4% on average, not significant | up to +23% |

On that benchmark, the one statistically significant difference in success was
between the two kinds of file: developer-written beat generated. Against no file
at all, neither showed a reliable gain. The extra cost was reliable for both.

Two details explain more than the averages:

- **Agents did what the files said.** When a file mentioned the tool `uv`,
  agents used it 1.6 times per task. When it didn't, almost never.
- **Codebase overviews didn't help.** Agents found the relevant files no faster
  with a tour of the repository than without one.

So context isn't weak. Agents follow it, including when it sends them on work
the task didn't need. That is how code behaves too: it runs whatever you wrote,
useful or not.

The study has limits. It covers only Python, ran each task once, and measured
whether tasks were resolved, not security or maintainability. A small benchmark
finding no significant effect has not proved there is none. But it is enough to
retire the idea that a longer file is a better one.

Length carries its own cost. Chroma tested 18 models and found performance
degrading as input grew, even on deliberately simple tasks<sup>[5](#ref-5)</sup>. Chroma
sells a vector database, so it has an interest in the subject. Anthropic, also a
vendor, offers a useful goal: "the smallest possible set of high-signal tokens
that maximize the likelihood of some desired outcome"<sup>[6](#ref-6)</sup>.

## Context has the same failures as code

| In code | In context |
| --- | --- |
| Dead code | Rules for a system you have since replaced |
| Conflicting logic | Two instructions that can't both be followed |
| Duplication | Facts copied from the README, now drifting apart |
| Missing types | "Write clean code", which nobody can check |
| Untrusted input | Fetched pages or issues that carry instructions |
| No tests | Nobody knows what changing a line would break |

Untrusted input deserves a warning. Ordinary programs can keep instructions and
data apart. A model reads both as text. Any context you didn't write should be
treated the way you treat a form submission, and real permissions should be
enforced outside the model.

## How to engineer it

### 1. Write only what the agent can't find out

For every line, ask: *could an agent learn this by reading the repository?* If
so, delete it. Directory listings and framework descriptions go first.

What survives is usually a decision, a trap or a boundary. Vidya's file has good
examples of each:

- **Decision:** add a new numbered migration; never edit one already applied.
- **Trap:** the dashboard's role switcher is a preview control, not
  authentication.
- **Boundary:** the service-role key is read only on the server, never in a
  client component.

The role switcher is the best of them. The code makes it look like
authentication, so reading the code is exactly how you would get it wrong.

### 2. If a machine can enforce it, take it out of prose

An instruction is a request. A type, lint rule, database policy or CI check is a
constraint. In Vidya, the rule that schools can't see each other's data belongs
in row-level security, and that is where it is. The instruction file only
explains that the policy, not the interface, is the real boundary.

Use prose for judgment. Use machinery for rules.

### 3. Give every fact a way to be checked

Vidya's file does this well elsewhere. A passage saying that all 14 dashboard
tabs use real data carries a date, admits that an earlier version was stale, and
includes a command to re-verify it. "As of this date, check it like this" ages
much better than "this is true".

The broken passage had no such check. One would have been short:

```bash
# Claim: "No test script exists in frontend/"
! grep -q '"test":' frontend/package.json
```

Put checks like this in CI. When the claim stops being true, the build fails and
someone fixes the sentence.

### 4. Test behavior, not wording

Checking facts doesn't tell you whether the file improves results. For that, run
an experiment:

1. Pick five to ten real tasks whose outcome you can check.
2. Run each several times without the file, and several times with it.
3. Compare success, cost and review corrections.
4. Remove one section at a time. If nothing changes, leave it out.

A handful of tasks won't give you a publishable result. It will show you
obvious waste, and it gives you a baseline to rerun when you change the file or
the model.

### 5. Fix the source, not just the output

When an agent makes a mistake, correct the result, then ask why it was possible:

- Could a check have caught it? Add the check.
- Was an existing instruction wrong? Fix or delete it.
- Was knowledge missing that the repository doesn't reveal? Add one line.
- Was it a one-off? Add nothing.

Try them in that order. Files bloat when every mistake becomes a new rule.

## We have come back to programming

Look at that list again: remove duplication, check claims, test behavior, fix
the source. We set out to stop writing code and arrived back at software
engineering, in a new package.

What changed is the unit of work. Traditional software is written as rules: if
this happens, do that. Now we increasingly write tasks: here is the outcome,
here are the limits, here is how we'll know it worked. The model fills in the
steps.

| | Traditional software | Task-driven software |
| --- | --- | --- |
| You write | Rules: how to do it | Tasks: what outcome, within which limits |
| Translated by | A compiler, same meaning every time | A model, which may vary between runs |
| A bug is | Wrong logic | Missing, stale or conflicting context |
| A test asks | Does this function return X? | Does this task succeed, and how often? |

It is a spiral more than a circle. Each earlier move up, from machine code to
assembly to high-level languages, also let us stop writing the layer below. But
a compiler preserves meaning, and a model interprets it. So the rules don't go
away. They become the boundary around the task: **tasks for judgment, rules for
guarantees.**

## Where the analogy breaks

Code is precise and, mostly, deterministic. Context is neither. The same file
can produce different results from one run to the next, and a model upgrade can
change its meaning without a single edit. That is an argument for more testing,
but it also means a passing test is evidence rather than proof.

Context also doesn't replace code. Production still runs code, and someone has
to understand it when it fails. Teams that keep the instructions and stop
reading the output will have moved their technical debt somewhere harder to see.

## Start with a deletion

Open the instruction file in your busiest repository. Find one line that is
false, one the agent could have discovered, and one that a tool should enforce.
Delete the first two. Turn the third into a check.

We spent decades learning that code is a liability as well as an asset: every
line has to be read, trusted and maintained. If code has come back as context,
that lesson came back with it. The best context file is the shortest one that still
changes the outcome.
